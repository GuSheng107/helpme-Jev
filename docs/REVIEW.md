> 审阅对象：`docs/DESIGN.md`（v3，2026-09-23）
> 审阅时间：2026-09-23　审阅人：奴才（以审阅者身份，非作者）
> 结论：**骨架完整、思路清晰，但有 6 处阻塞性问题必须先在文档层面解决，否则开工即返工。**

## 一、总体评价

**优点**：分层清楚（需求 → 契约 → 数据 → 服务 → 阶段），关键设计有出处（抄 Jarvis / hlg 而非凭空发明），
诚实原则（MBTI 标注科学性）与红线（admin 不看日志）写得到位。

**主要风险**：文档在**核心链路的中段是空的** —— "LLM 分析"产出什么、记忆复盘何时触发、
一次操作到底花几次上游调用，这三件事没定义。这三处不补，P3/P4 阶段没法落地。

## 二、P0 阻塞问题（必须先解决）

### P0-1 「未配 LLM 时」的行为自相矛盾 ⚠️

| 位置 | 说法 |
|---|---|
| §1 需求 1 | 未配 LLM 时聊天场景**只出判断、不出候选** |
| §10 | **必须有**：未配置时聊天场景**返回明确错误** |

一个说降级运行、一个说直接报错。必须二选一。

**建议**：取 §10（报错），因为需求 1 明确"必须有 LLM"；同时 §1 改为"未配 LLM 时聊天场景不可用，仅提示去配置"。

### P0-2 「LLM 分析」的产出物没有定义 ⚠️ 核心链路最大空洞

§8.4 第 ③ 步写"LLM 分析：理解情境、提取要点，**输出结构化分析**"，但：

- 这个"结构化分析"**长什么样**？谁消费它？
- 既然决策由 JEV 出，LLM 的分析结果**如何进入决策**？还是说纯粹给用户看？
- ④ 翻译桥说"与 LLM 分析**合并执行**"，那这次调用的 prompt 要同时干"分析 + 翻译"，输出结构是什么？

**建议**：在 §8.4 补一张**该步骤的输入/输出 schema**。奴才倾向：一次调用同时产出
① 英文版上下文（供 JEV）② 中文分析要点（供用户看）③ 待追问项（若有），三合一。

### P0-3 记忆复盘在主链路里消失了

§8.4 链路 ①–⑪ **只有"⑧ 人设更新"，没有记忆复盘**；但 §8.8 说记忆由复盘产出。
需求 15（记忆治理）与主链路**没有接上**。

**建议**：明确复盘触发点 —— 是"每次分析后顺带"？还是"消息累积到 N 条"？还是"用户手动"？
（§8.8 列了三个触发条件但没说优先级，且未体现在链路图中。）

### P0-4 没有上游调用的成本约束 ⚠️ 产品级风险

按链路自算，**一次聊天分析至少 5 次上游调用**：

```
LLM 分析(+翻译) → JEV 判断 → JEV 人设建模 → LLM 起草 → JEV 排序
```

若再触发追问（**轮次不设上限**）、润色、记忆复盘，次数继续叠加。
而**费用是用户自己的 key 出的**。

**建议**：① 链路图标注每次调用；② 给"一次操作的最大调用次数"上限或提示；
③ 追问"不设上限"建议加**软提示**（如连续 5 轮后提醒用户"可跳过追问直接出结果"）。

### P0-5 LLM 的 64K 预算与"用户自配任意模型"矛盾

§8.5/§14 定"LLM 统一 64K token"，但需求 2 允许用户配**任何** OpenAI 兼容模型 ——
可能是 8K 窗口的小模型，也可能 200K。**硬编码 64K 会与实际不符**（超限直接报错）。

**建议**：设置项增加"上下文窗口大小"，默认 64K、用户可改；并在请求前按实际窗口裁剪。

### P0-6 JEV 协议被隐性假设为"System One 兼容"

§9.1 说"用户填完整端点 URL，系统不做任何推断"，但请求体固定为
`{model, state, questions}` 且题型限 noul/choice/score —— **这已是强协议约束**，
文档却没说清"只支持 System One 协议"。

**若皇上的 JEV 是自研的不同协议，§9 整节要重写。**

**建议**：§9.1 明确写"**仅支持 System One 协议**（noul / choice / score）；
不兼容者需在 `clients/jev_client.py` 加适配层"。

## 三、P1 重要问题

| # | 问题 | 建议 |
|---|---|---|
| P1-1 | **字段引用失效**：§8.5 装配表仍写 `memories.emotion_trend`，但 §4 中 `memories` 已改成条目化结构、**该字段已不存在** | 情绪轨迹改由记忆条目（`category=情绪模式`）承载，或单列一张表 |
| P1-2 | **记忆与人设的判定边界模糊**："她生气会冷战"既是行为事实（记忆）又是冲突风格（人设）→ 会双份存储、更新不同步 | 定判定规则（记忆=可陈述事实，人设=可归类的维度），或规定人设题**只吃记忆条目**、不直接吃原始对话 |
| P1-3 | **人设题目集的归属未定义**：是每个场景各自一套，还是全局共用？（DISC 只适用于职场） | 建议：人设题集**挂在场景上**，随场景切换 |
| P1-4 | **`counterpart_key` 的生成规则空缺**：怎么判定"同一对象"？靠名字？手动关联？导入记录算什么？ | 建议：默认取 `counterpart_name` 归一化，允许用户手动合并 |
| P1-5 | **阶段顺序与依赖不符**：P7 才做"会话/消息落库"，但 P2（装配）、P3（判断）、P4（分析）**都要读会话消息** | 重排：**P0/P1 就把全部表建好 + 会话/消息 CRUD**，后续阶段只加逻辑 |
| P1-6 | **缺少错误处理与降级设计**：JEV 超时/429/失败、LLM 失败时怎么办？只有 §9.4 一个字段级重试 | 补一节：超时值、退避策略、失败后的用户提示与可重试入口 |
| P1-7 | **候选 3~5 条 vs JEV 固定 criteria**：Jarvis 是**硬性 3 条**且已校准，改 3~5 需重新校准；criteria 键也要动态生成（`reply_a`…`reply_e`） | 补"重新校准"任务，并在构造器支持动态键数 |
| P1-8 | **`call_logs` 体积与清理策略缺失**：明文存完整 state/questions/answers，一次操作 5+ 条，无保留期、无索引/分页设计 | 补保留期（如 30 天滚动删除）+ 索引（trace_id/owner/created_at）+ 单条 body 大小上限 |

## 四、P2 改进建议

1. **缺部署与运维章节**：Docker、备份、迁移（hlg 是 `SCHEMA_VERSION` 严格校验，本项目沿用但没写）、健康检查、日志轮转
2. **缺数据导出 / 账号注销**：聊天记录属敏感个人数据，应支持导出与一键清空（Jarvis 有 PRIVACY.md）
3. **缺测试策略章节**：目前只有红线里一句"跑通测试"；建议明确单测 / 集成 / 契约测试范围（尤其 jev_client、翻译桥、脱敏）
4. **缺性能目标**：一次分析的目标响应时间（JEV ~1s + LLM 若干秒）
5. **§3 项目结构未跟上设计**：缺 `persona_questions.py`、`memory_service.py`、`import_service.py`、`polish` 相关文件
6. **`admin/` 目录名误导**：本项目前端是**用户端 + 管理**混合，沿用 hlg 的 `admin/` 会让人以为是管理后台，建议改 `web/`
7. **§11 缺会话 CRUD**：只有 `GET conversations/messages`，没有创建/重命名/删除会话、发消息的接口
8. **§12 缺「记忆管理」页**：记忆条目查看/编辑/撤销复盘没有落点
9. **术语不统一**：`trace_id` 与 `traceId` 混用；面板文案里的"她"是恋爱专属，通用场景不该出现
10. **§8.2 职场场景题目集只说"同结构"**：实际需要业务输入，建议列为待办并标注"需人工设计"
